# 应用内更新检查与下载（M5）

> 用户 2026-10-10 提出：「能不能做到类似于明日方舟 MAA 那种热更新推送？
> 就是不用用户再去网站下载更新安装包，直接给现有软件推送更新公告和下载按键。」
>
> 状态：**设计已定，开始实现**。界面风格参照 MAA 的更新弹窗。

---

## 一、MAA 实际是怎么做的（读源码，不是猜）

参照对象是 `MaaAssistantArknights`，相关代码在：

| 文件 | 作用 |
|---|---|
| `src/MaaUpdater/main.cpp`（2290 行） | 独立的 `MAA.Updater.exe`，负责替换文件 |
| `src/MaaWpfGui/ViewModels/Dialogs/VersionUpdateDialogViewModel.cs` | 检查更新、下载、写更新计划 |
| `src/MaaWpfGui/Views/Dialogs/VersionUpdateDialogView.xaml`（68 行） | 更新日志弹窗 |

### 1. 它不是增量更新

MAA 的 Release 资产是**全量包**：`MAA-v6.18.0-win-x64.zip` **270.5 MB**，
一次下完整个程序。所谓"热更新"只是"不用去网站手动下载"，
**不是"只下变化的那几 MB"**。这一点必须先说清楚，否则预期会错。

### 2. 换文件靠一个独立进程

Windows 上**运行中的 exe 无法替换自己**，所以 MAA 拆成两步：

1. 主程序下载整包，写一份**更新计划**（`PendingUpdatePlan`，只有三个字段）：
   - `removeList`：要删的文件
   - `moveList`：要移动的文件
   - `relaunchArgs`：重启时传给主程序的参数
2. 主程序退出，`MAA.Updater.exe <父进程ID> <根目录> <解包目录> <备份目录>`
   启动：**等父进程真正退出** → 替换文件 → 失败回滚 → 重新拉起主程序，
   期间自己画一个进度窗口。

### 3. 数据源

```
repos/.../MaaRelease/releases              更新包源
repos/.../MaaAssistantArknights/releases/latest   版本信息
version/summary.json                       自建清单
MirrorChyan                                国内镜像（需 CDK）
```

启动时检查，开关叫 `StartupUpdateCheck`。

### 4. 它的设置项（值得抄的部分）

| 设置项 | 含义 |
|---|---|
| 启动时检查更新 | 启动时拉一次版本信息 |
| 定时检查更新 | 按游戏内时间定期检查 |
| 自动下载更新包 | 关掉后**只提示、附下载链接**，用户自己下 |
| 自动安装更新包 | 检测到新版本后**不弹窗**，任务空闲时自动更新并重启 |
| 更新渠道 | 正式版 / 公测版 / 内测版 |
| 更新源 | 全局源（GitHub + 国内直连镜像）/ Mirror酱 |
| 显示更新程序进度窗口 | 替换文件时是否显示独立进度窗 |

⚠️ **注意最后两项的取舍**：MAA 提供了「关掉自动下载」和「关掉自动安装」，
也就是说**默认行为可以退化成「只提示、给链接」**。这个降级路径对我们很重要，
见下面第五节。

## 二、我们的技术条件

| 条件 | 现状 | 结论 |
|---|---|---|
| 网络请求 | `pcbart/short_url.py` 已用 `urllib`，无第三方依赖 | **可复用，不引入新依赖** |
| Qt Network | 打包时排除（`PySide6.QtNetwork`） | **不需要启用**，用 `urllib` 即可 |
| 静默安装 | Inno Setup 的 `AppId` 固定不变 | 同 `AppId` 的安装包**原地升级**，支持 `/VERYSILENT` |
| 安装包体积 | **50 MB**（MAA 的五分之一） | 下载体验比 MAA 好 |
| 分发链路 | GitHub Release + CNB Release，下载直链**匿名可用** | 已有 |
| 设置存储 | `pcbart/ui_theme.py` 的 `load_settings` / `save_settings` | 加开关不用新机制 |
| 列表控件 | 现有 `FloatingPanel` + `section()` 模式 | 能复用 |

### 更新源的实测结果

| 源 | 结果 |
|---|---|
| GitHub API | ✅ 本机直连 200（0.58s），但**国内用户不挂代理常超时**（本机历史记录里就是直连 GitHub 6/6 超时） |
| CNB Release API | ❌ **401，必须登录**：`The task will not run because the user is not logged in` |
| CNB 下载直链 | ✅ 匿名 200，50,144,467 字节 |
| **自家网站** `www.xikaaa.cn` | ✅ 静态站，Caddy 直托管，国内可达性好 |

⚠️ **关键约束**：CNB 的 **API 需要登录，但下载直链匿名可用**。
所以 CNB 只能当"下载源"，不能当"版本查询源"。

## 三、定案：检查走自家站，下载走 CNB

```
        应用启动
           │  后台线程，超时 3 秒，失败静默
           ▼
  https://www.xikaaa.cn/update.json          ← 版本清单（几 KB）
           │
           │  version 比本地高？
           ▼
    弹出更新公告（版本号 + 更新日志 + 下载按钮）
           │  用户点【下载并安装】
           ▼
  https://cnb.cool/xikaaa/Ez_PCBart/...       ← 安装包（50 MB，不占服务器带宽）
           │  下载 → 校验 SHA-256 → 启动安装包 → 主程序退出
           ▼
        Inno 原地升级（AppId 不变）
```

### 清单格式

网站加一个静态文件 `public/update.json`（由发布脚本生成，**不手写**）：

```json
{
  "version": "1.1.0",
  "date": "2026-11-xx",
  "notes": [
    "新增：更新检查与下载，应用内直接获取新版本",
    "改进：安装包与程序文件改用 EzPCBArtTool 命名",
    "修复：……"
  ],
  "download": "https://cnb.cool/xikaaa/Ez_PCBart/-/releases/download/v1.1.0/EzPCBArtTool_v1.1.0_安装包.exe",
  "size": 50143110,
  "sha256": "……",
  "download_page": "https://www.xikaaa.cn/tools/pcb-art/"
}
```

⚠️ **`notes` 的文案风格**必须遵守 `AGENTS.md` 第 7 节（按新增/改进/修复分类、
短句陈述、不写开发过程）。**由发布脚本从 `releases/pcb-art-v*.md` 的
`changes` 字段生成**，保证网站更新日志、GitHub Release 正文、应用内公告
**三处同源**，不会各写一份。

⚠️ **`download_page` 是兜底**：CNB 挂掉或用户网络异常时，
至少有网页入口，不会把用户堵死。

## 四、界面（模仿 MAA）

### 1. 更新公告弹窗

MAA 的弹窗结构极简：**顶部居中显示版本号，下面整块是 Markdown 渲染的更新日志**，
没有多余装饰。我们照这个结构，用现有 MD3 主题实现：

```
┌─────────────────────────────────────────┐
│                                         │
│              v1.1.0                     │   ← 20pt 粗体，居中
│                                         │
│  ┌───────────────────────────────────┐  │
│  │ 新增                              │  │   ← Markdown 渲染
│  │  · 更新检查与下载…                │  │
│  │ 改进                              │  │
│  │  · 安装包改用 EzPCBArtTool 命名…  │  │
│  │ 修复                              │  │
│  │  · ……                             │  │
│  └───────────────────────────────────┘  │
│                                         │
│      [ 稍后 ]        [ 下载并安装 ]      │   ← 右下角
└─────────────────────────────────────────┘
```

**与 MAA 的差异**（我们有而 MAA 弹窗里没有的）：
MAA 把下载按钮放在别处（设置页的「软件更新」），弹窗只展示日志。
我们要在弹窗里直接给下载按钮——这正是用户提的需求。

### 2. 设置面板新增一节

在【视图 → 界面设置…】里追加（现有已到第 4 节）：

```
5 · 更新
  [✓] 启动时检查更新
  [ ] 自动下载并安装        ← 默认关，见第五节
  当前版本：1.0.0
  [ 立即检查更新 ]          ← 手动触发，永远可用
```

⚠️ **「立即检查更新」不能依赖自动检查的开关**。这是本项目的既有教训：
「功能只有脚本在调」踩过两次（见 `pcb-automation-must-stay-editable`）。
自动检查关掉了，手动入口必须还在。

### 3. 下载进度

不做百分比进度条（同网站下载按钮的理由：**CNB 的 CDN 会拒绝带 `Origin` 的请求**，
`fetch` 拿不到流）。用不定量反馈 + 已下载字节数的文本更新。

### 4. ⚠️ 按钮必须放在面板的固定页脚里

第一版把「状态文字 + 两个按钮」和更新日志放在同一个 `content_layout` 里，
**结果是一个真 bug**：`FloatingPanel` 本身已经有滚动区，我又在里面嵌了第二个
`QScrollArea`；长更新日志一到，内容高度涨到 517 px 而面板只有 470 px，
**两个按钮和下载进度一起掉到面板外面**——恰好是用户点了下载、最需要看到
进度的时候。

修法：删掉嵌套滚动区，按钮与状态改挂 `FloatingPanel.set_footer()`。
`set_footer` 的 docstring 里写着它就是为这种情况准备的
（「In the scrolling area it sat ~380 px below the fold on this panel, so the
button that actually applies the settings was the one thing the user could
not see」）—— 同一个坑，这个项目里踩过第二次。

**测试**：`test_buttons_stay_visible_with_a_long_changelog` 与
`test_status_line_is_visible_while_downloading` 用 40 条说明把内容撑高，
断言「没有第二层滚动区」「按钮不在滚动区里」「按钮与状态文字的底边都在面板高度以内」。
**注入验证**：把按钮挪回 `content_layout` → 两条测试变红。

⚠️ **这类问题只有渲染截图才能发现**：几何断言当时全绿（Qt 的布局会报
一个「合理的」几何值），是肉眼看截图才看出按钮不见了。

## 五、⚠️ 默认行为必须保守

用户提的是「推送更新公告和下载按键」，**不是「静默自动升级」**。
按 MAA 的教训和本项目一贯的保守风格：

| 行为 | 默认 | 理由 |
|---|---|---|
| 启动时检查更新 | **开** | 用户要的就是这个 |
| 自动下载并安装 | **关** | 静默替换用户的程序是破坏性动作；MAA 也把这个做成可选 |
| 检查失败 | **静默** | 不联网也要能正常用软件，不能弹错误 |
| 下载后 | **启动安装包，主程序退出** | 需要实测 Inno 在 `/SILENT` 下的行为 |

⚠️ **不做「静默自替换」**（MAA 那种独立 Updater.exe）。理由：

1. 用户的需求是「不用去网站下载」，弹窗 + 一键下载已经满足；
2. 自替换需要额外写一个 updater 程序，且失败时可能把用户程序弄坏；
3. 我们的包只有 50 MB，用户点一下的成本很低。

如果以后确实需要，再照 MAA 的方式补 `updater.exe`，
**这一版先不做**。

## 六、⚠️ 与 1.1.0 改名的排期冲突

`docs/PACKAGING.md` 的「命名规则」一节定了 1.1.0 要改程序名与安装目录
（`PCB艺术板工具` → `EzPCBArtTool`）。

如果**更新检查先发、改名后发**，用户从 1.0.0 升到 1.1.0 时：
- 安装包会装到**新目录** `EzPCBArtTool\`
- 旧目录 `PCB艺术板工具\` **残留**，出现两份安装

**所以顺序必须是**：**改名先发生，更新检查后生效**。

**定案：两件事放在同一个版本（1.1.0）里发布。**

理由：1.0.0 没有更新检查，所以 1.0.0 → 1.1.0 这一步**无论如何都是用户手动下载**，
改名的一次性代价（手动卸载旧版）在这一步已经付掉了。等 1.1.0 装好，
路径已经是新的，之后 1.1.0 → 1.2.0 走应用内更新就是干净升级。

⚠️ **不能反过来**（更新检查先发、改名后发）：那样 1.1.0 的更新器会把
改名后的 1.2.0 装到新目录，而旧目录留在原地，用户也不会被提醒去卸。

⚠️ 这也意味着本文档描述的 `update.json` 里 `download` 指向的
**必须是改名后的包**（`EzPCBArtTool_v*.exe`）。

⚠️ **1.0.0 的用户拿不到自动提示**（那个版本里没有这段代码），
所以 1.1.0 的 Release 说明和网站都要照常写清楚怎么手动下载。

## 八、验收方式

本项目的既有规矩：**「文件能打开」不算证据**。这件事的验收要包含：

1. **注入验证**：把版本比较改成字符串比较 → 测试必须红（抓 `1.10.0` 这类）
2. **端到端**：本地起一个假的 `update.json`，跑打包后的程序，
   确认弹窗出现、下载、校验、启动安装包全链路
3. **断网测试**：拔网线/改 hosts，确认软件正常启动、不弹错误、不卡顿
4. **实测 Inno 静默升级**：装 1.1.0 → 用 1.2.0 的包 `/SILENT` 装 →
   确认原地升级、程序目录没有残留旧文件

## 九、未决问题

1. **弹窗要不要在程序启动时就出现？** MAA 是启动时检查。
   建议**延迟 5 秒**再弹，避免和启动动画抢注意力，也让启动更快。
2. **同一天多次启动是否重复提示？** 建议记住"这次版本已经提示过"
   （存 `settings.json`），同版本只提示一次，但手动检查永远可用。
3. **下载中断怎么办**？**已实测支持断点续传**：CNB 直链返回
   `206 Partial Content`，`Range: bytes=0-99` 正确返回 100 字节。
   所以下载器要发 `Range` 头续传，50 MB 在国内网络下有断的可能。

## 十、实测记录（2026-10-10）

| 检查项 | 命令 | 结果 |
|---|---|---|
| CNB 下载直链匿名可用 | `curl -I -L <直链>` | ✅ `200`，`Content-Length: 50144467` |
| CNB 支持断点续传 | `curl -r 0-99 <直链>` | ✅ `206`，返回 100 字节 |
| CNB API 匿名可读 | `curl <api.cnb.cool/.../-/releases>` | ❌ **401**，需登录 |
| GitHub API 本机直连 | `curl api.github.com/.../releases/latest` | ✅ `200`（0.58s），但**国内用户不挂代理常超时** |
| 自家站点 | `curl www.xikaaa.cn/...` | ✅ `200`，Caddy 静态托管 |

⚠️ **`Accept-Ranges` 响应头在 HEAD 里没返回**（只有 `Content-Length`），
但**实际发 `Range` 请求会得到 206**。所以不能靠 HEAD 判断是否支持续传，
要么直接试，要么无条件带 `Range` 并按响应码分支。

⚠️ **`docs/PACKAGING.md` 的命名规则已经定了 1.1.0 改名**
（`PCB艺术板工具` → `EzPCBArtTool`），所以本文档
`update.json` 里的 `download` 字段必须指向**改名后的包名**。
