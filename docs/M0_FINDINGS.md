## 二、单位系数：文件内自证

这是 M0 最关键的产出，而且**不依赖任何外部资料**——样本工程里有一条尺寸标注，
EasyEDA 自己把测量结果写成了文字。

```
标注两端坐标跨度 : 3932.0079 单位
EasyEDA 标注文字 : "99.873mm"

3932.0079 × 0.0254 = 99.8730 mm      ✓ 偏差 0.0000%
```

如果按官方规范正文写的 `0.01 inch`（= 0.254 mm）解释，同一跨度会变成 **998.73 mm**，
接近一米；按 `0.01 mm` 解释则是 **39.32 mm**。两者都与标注文字矛盾。

### 交叉验证

三项独立证据全部指向 0.0254：

1. **文件内自证**（上面，0.0000% 偏差）
2. **KiCad 官方 EasyEDA Pro 导入器**：`ScaleSize(v) = KiROUND(v * 25400.0 / 500.0) * 500`，
   KiCad 内部单位为 1 nm，展开即 `v × 0.0254 mm`
3. **社区解析器 epro2x**：`MIL_TO_MM = 0.0254`，注释记录了同样的实测过程

### 与官方规范正文的冲突处理

官方 V3 规范第 8 行写"所有坐标、长度、大小统一使用 `0.01 inch` 为单位"，
与实测相差 10 倍。**以实测为准**，理由：

- 规范里的示例数值（`width: 0.7`、坐标 `100`/`200`）是自动生成的占位符，
  按任何系数解释都会得到荒谬结果（0.018 mm 线宽 / 0.9 mm 板宽），无法自证
- 真实文件里出现的是 `24.0158`、`4.9213`、`3932.0079` 这类带 4 位小数的值
- 若按 0.01 inch 实现，生成的板子会比预期大 10 倍，装配必然失败

### 其他实测数值

| 语义 | 单位值 | mm |
|---|---|---|
| 默认过孔外径 | 24.0158 | 0.6100 |
| 默认过孔内径 | 12.0078 | 0.3050 |
| 板框线宽 | 4.9213 | 0.1250 |
| 默认走线宽度 | 10 | 0.2540 |
| 1 mm | 39.3701 | 1.0000 |

存储精度：**4 位小数**。因此 1 mm 存为 39.3701（而非 39.3700787…），
往返误差量级为 `0.5 × 0.0254 × 10⁻⁴ = 1.27e-6 mm`，完全可忽略。

## 三、Y 轴方向

文件使用**屏幕坐标系，Y 向下增大**。证据：

1. KiCad 导入器的 `ScalePos` 实现为 `(-ScaleSize(x), -ScaleSize(y))`，
   对 Y 取负，说明需要翻转才能进入设计坐标系
2. 样本中尺寸标注的端点跨度为 `y ∈ [-972.0079, 2960]`，标注文字
   `y = 753.2461` 落在两端点之间，符合屏幕坐标的视觉居中

**工程约定：内部一律使用 Y 向上（设计坐标系），只在编解码边界取负。**
该转换实现在 `pcbart/primitives.py` 的 `convert_path_to_mm` / `record_to_mm` 中，
且对路径内的 Y 分量一视同仁——板框路径里嵌着 `ARC` 的端点 Y，漏掉就会画歪。

### 验证实例

样本板框原始坐标为 `x ∈ [1140, 3103.5]`、`y ∈ [-972, 2960]`。
转换后：

```
宽 : (3103.5039 - 1140) × 0.0254 = 49.873 mm
高 : (2960 - (-972.0079)) × 0.0254 = 99.873 mm
```

宽 × 高 = **49.873 × 99.873 mm**，与文件内标注的 99.873 mm 完全一致。

## 四、记录格式细节

### 4.1 行结构

```
{"type":"POLY","ticket":351,"id":"b5a139be9c01fa4e"}||{"layerId":11,...}|
```

- 分隔符 `||`，行尾以 `|` 结束
- JSON 为紧凑格式（无空格）
- **已确认的边界情况**：`RULE_SELECTOR` 记录的空载荷写作
  `{...}|||`（两个分隔符后直接一个终止符）。解析器必须区分
  「载荷为空字符串」和「载荷缺失」，否则会误判为解析失败
- 部分记录的 `id` 字段本身是 **JSON 数组的字符串形式**，
  例如 `"[\"LAYER\",1]"`、`"[\"PRIMITIVE\",\"ALL\"]"`。
  因此不能用朴素的字符串切割来定位 `||`

### 4.2 一致性模型

- `ticket` 是文件内全局自增计数器；同一 `type` + `id` 出现多次时 **ticket 大者胜**
- 删除原子数据 = 用更高 ticket 写入空载荷
- 这意味着**修改已有工程可以只追加记录**，无需重写整个文件

### 4.3 文档顺序

实测样本的段顺序：

```
SYMBOL → DEVICE → BOARD → SCH → SCH_PAGE → PCB → CONFIG → PANEL → BLOB → FONT
```

**记录归属于它前面最近的那个 `DOCHEAD`。** 因此新图元要插到目标段（如 `PCB`）
的末尾，也就是下一个 `DOCHEAD` 之前——仅仅"排在 `BLOB` 之前"是不够的，
因为 `CONFIG` 和 `PANEL` 都夹在 `PCB` 与 `BLOB` 之间。

本项目的生成器用 `EproDocument.append_to_section(record, doc_type="PCB")` 实现该约束。
这一点最初做错了，详见第七节缺陷 2。

## 五、板框的实际画法

样本中板框由 **10 条独立的 `POLY` 记录**组成，全部在 layerId 11：

```json
{"type":"POLY","id":"4da720d3497138c6"}||{
  "partitionId":"","groupId":0,"netName":"","layerId":11,
  "width":4.9213,
  "path":[1140,2919.9381,"L",1140,-930.8044],
  "locked":false,"zIndex":-1,"polyType":"NORMAL"}|]
```

要点：

- 一条 `POLY` 只存**一段**路径（一段直线或一段圆弧），10 段首尾相接拼成完整轮廓
- 直边用 `L` 模式，圆角用 `ARC` 模式（带角度）
- `polyType` 固定为 `"NORMAL"`
- 生成器采用**单条 `POLY` 闭合折线**表达矩形轮廓，更简单且便于验证
- 面积填充（`FILL`）的 `width` 是描边宽度，**不是**走线宽度——
  样本中为 `0.2`/`1`，若当成走线检查会误判为违规

## 七、验证过程中发现并修正的两个缺陷

离线自测通过后，用**独立实现**（Node 版 ZIP+日志校验器 `tools/verify_epro2.mjs`，
不共享任何 Python 代码）复核生成的文件，抓到两个自测没能发现的问题。
这两个都是"文件能打开但内容不对"的类型，值得记录。

### 缺陷 1：`project2.json` 元数据不完整

- **现象**：写了 30 字节，内容只有 `{"title": "..."}`
- **原因**：`EproArchive` 直接采用调用方传入的元数据字典，而生成器只传了标题
- **后果**：缺少 `cbb_project` / `editorVersion` / `introduction` / `description` / `tags`，
  EasyEDA Pro 读取时可能报错或行为异常
- **修复**：`EproArchive` 改为把调用方元数据**合并到默认值之上**，字段缺失自动补齐
- **回归**：`test_partial_metadata_is_completed`、`test_archive_accepts_no_metadata_at_all`

### 缺陷 2：板框被插进了错误的文档段（更严重）

- **现象**：板框 `POLY` 记录落在 `CONFIG` 段，而不是 `PCB` 段
- **原因**：`append_before_blob()` 为了满足"插在 BLOB 之前"这条约束，
  把图元插到了 `BLOB` 段前面；但文档顺序是
  `... PCB → CONFIG → PANEL → BLOB ...`，
  而记录归属于**它前面那个 DOCHEAD**，于是板框成了 `CONFIG` 的图元
- **后果**：编辑器打不开报错不至于，但**不会把这条轮廓当成板子的几何数据**
- **修复**：新增 `EproDocument.append_to_section(record, doc_type)`，
  把记录插到目标段末尾（下一个 DOCHEAD 之前）
- **回归**：`test_append_to_section_places_record_inside_that_section`、
  `test_outline_is_filed_under_the_pcb_document`

### 教训

**"插在 BLOB 之前"是必要不充分条件。** 格式规范只说了新数据不能排在 BLOB 之后，
但真正决定归属的是最近的那个 DOCHEAD。仅靠自测（自己写、自己读）发现不了这类问题，
因为读写两端犯同样的错误就会互相印证——独立实现的校验器是必需的第二意见。
